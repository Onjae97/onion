# aspice-law.md — ASPICE 업무 공통 운영 지침

> 이 문서는 `onion` 저장소에서 Automotive SPICE(이하 ASPICE) 관련 업무와 자동화를 할 때 사람과 AI 에이전트(Claude 등)가 따르는 공통 원칙이다. 공식 ASPICE 모델 문구의 복사본이 아니라, v3.1 모델과 사용자 운영 결정에 기반한 내부 지침이다.

## 0. 용어와 지침 체계

- **ASPICE / CL**: Automotive SPICE v3.1 프로세스 평가 모델과 능력수준(Capability Level). 자동화 도구의 구현만으로 프로세스 능력수준 달성을 주장하지 않는다.
- **SUP.8 / CM**: 형상관리 프로세스와 이를 수행·지원하는 업무. 현재 이 저장소의 주 업무 범위다.
- **CI / 베이스라인 / WP**: 형상항목 / 확정된 구성 상태 / 업무 수행의 증거인 산출물. 실제 프로젝트 시스템(Codebeamer·Confluence 등)의 기록과 이 저장소의 자동화 결과를 구분한다.
- **정본**: 해당 업무에 대해 사용자가 지정하거나 승인한 기준 문서·양식·시스템 기록. 출처와 적용 시점을 기록한다.
- **지침의 역할**: 이 `aspice-law.md`는 ASPICE 업무 공통 원칙, 각 도구의 `SKILL.md`(예: `CA-automation/traceability/SKILL.md`)는 실행·판정 세부 절차, `CA-automation/README.md`의 공통 원칙은 CA 도구 모음의 운영 원칙을 맡는다. 하위 지침이 공통 원칙과 충돌하면 임의로 한쪽을 적용하지 말고 충돌을 보고한다. 사용자 지시가 우선한다.

## 1. 목적과 적용 범위

1. ASPICE v3.1을 기준으로 CM 담당자의 업무(현재 HL클레무브 상주, ADCU50)와 관련 자동화를 지원한다. SUP.8 BP1~BP9와 PA 2.1·2.2는 목표 추적의 기준으로 쓰되, 실제 충족 여부는 승인된 평가 근거로 별도 확인한다.
2. 현재 구축된 자동화는 **AUTO-001 추적성 Gap Matrix**(`CA-automation/traceability/`)다. 판정 규칙의 정본은 해당 `SKILL.md`이며, 이 문서는 공통 원칙만 규정한다. 준비 자료나 시험 코드의 존재를 자동화 구축 완료로 표현하지 않는다.
3. 실제 제품 CI의 식별·변경 승인·브랜치·베이스라인 설정은 해당 프로젝트의 권한 있는 시스템과 담당자가 수행한다. 이 저장소의 도구는 데이터 수집·대조·초안 작성·상태 보고를 지원한다.
4. SUP.8 외 프로세스(SUP.1·SUP.9·SUP.10, SYS/SWE 추적성 등)로 업무를 넓힐 때는 이 문서의 범위 항목과 부록 A를 함께 개정한다.
5. 적용 모델을 4.0 등으로 전환할 때는 승인된 전환일·프로젝트 범위·BP/GP와 WP 대응표를 함께 개정한다. **3.1과 4.0은 BP 번호·이름이 다르므로** 서로 다른 버전의 기준을 한 회차에 섞지 않는다.

## 2. AI 에이전트 공통 원칙

1. 요청 범위, 원본, 기준일, 프로젝트·회차, 적용 양식, 출력 경로를 확인한다. 요청과 무관한 기능 추가·리팩터링은 하지 않는다. 사용자만 결정할 수 있는 판정 기준과 예외는 확정하지 않고 묻는다.
2. 현재 파일·API 응답·승인된 기준 문서를 직접 확인한다. 기억, 과거 대화, 이름만 비슷한 파일을 현재 근거로 삼지 않는다. 열람에 실패하면 확인하지 못했다고 밝힌다.
3. ASPICE 근거를 적을 때는 **버전 + 프로세스 ID + BP/PA**로 쓴다(예: `ASPICE 3.1 SUP.8.BP8`). 근거를 모르면 지어내지 않고 "근거 확인 필요"로 남긴다. 표준 문구는 길게 옮기지 않고 요약하며, ASPICE 요구·고객사 요구·사내 규칙을 구분해 적는다.
4. AI는 **능력수준이나 N/P/L/F 등급을 최종 판정하지 않는다.** 증거와 Gap을 정리해 제시하고, 판정은 평가자·담당자가 한다.
5. 비밀번호·토큰·회사 주소·사내 상세 값은 파일·로그·채팅·저장소에 남기지 않는다. 로그인 정보는 Windows 자격 증명 관리자에만 두고, AI는 비밀번호를 묻거나 받지 않는다. DRM을 우회하거나 복호화 사본을 만들지 않는다.
6. 초안 작성과 최종 승인·서명을 분리한다. 공식 산출물 반영·저장·서명은 사람이 한다.
7. 파일 삭제·이동·교체, 이력 재작성 등 되돌리기 어려운 작업은 대상과 영향을 확인하고 승인을 받는다.

## 3. CM 업무 수행 원칙

1. **식별과 상태**: CI·문서·요구사항을 이름이 아니라 고유 식별자, 버전, 출처, 기준 시점으로 식별한다. 실제 저장소·베이스라인 상태를 추측해 기입하지 않는다.
2. **변경 통제**: 변경 목적·요청자·영향 대상·변경 전후 값·검증 결과·승인 상태를 기록한다. 정본 산출물 변경은 프로젝트 승인 절차를 따른다.
3. **데이터 대조와 검증**: 대상 범위와 예외를 먼저 확정하고, 수집의 완전성과 식별자 단위 관계를 검증한다. 추적성의 구체적 판정은 AUTO-001 `SKILL.md`를 따른다.
4. **형상 상태 보고**: 실제 시스템에서 관찰한 상태를 기준 시각과 함께 보고한다. 조회 실패나 미수집을 0건으로 보고하지 않는다. 회차 간 변경을 구분한다.
5. **능력수준**: BP·PA와 산출물의 연결을 기록하되, 일부 자동화의 완료를 CL 평가 결과로 표현하지 않는다.

## 4. 데이터와 시스템 연동

1. **조회는 읽기 전용**이다. Codebeamer·Confluence에는 GET 요청만 하고 쓰지 않는다.
2. **Excel**: DRM 문서는 Excel COM(별도 인스턴스)으로 읽기 전용으로 열고 저장하지 않고 닫는다. 이미 열린 Excel 세션에 붙거나 같은 이름의 다른 폴더 파일을 대상으로 추정하지 않는다. 병합 셀·수식·서식·수기 영역을 고려하고, 저장한 결과는 다시 열어 확인한다.
3. **추적성 데이터**: Codebeamer 접근, 대상·관계 판정, 보고서 형식은 AUTO-001 `SKILL.md`를 정본으로 따른다.
4. 근거가 없거나 조회에 실패하면 자동 판정을 멈추거나 `확인불가`로 표시한다.
5. 출력 파일은 실행 시각, 기준 파일(CI list 등)과 조회 시점으로 연결해 어떤 근거로 만든 결과인지 추적할 수 있게 한다.
6. 실제 값은 `config.json`(Git 제외)에만 두고, 저장소에는 가짜 값의 `config.example.json`만 올린다.

## 5. 자동화 개발과 운영

1. 판정 규칙·양식·프로젝트 설정은 도구별 `SKILL.md`와 설정 파일에 둔다. 공통 원칙을 복제해 서로 다른 버전으로 방치하지 않는다.
2. `미수집/조회 실패(확인불가)`, `0건`, `N/A(비대상)`, `미추적(NG)`을 조건에서 구별한다. 근거 부재를 기본값·빈 목록·성공 판정으로 바꾸지 않는다. 기존의 실패 중단을 단순 건너뛰기로 바꾸지 않는다.
3. 판정 등급은 도구별 결정을 따른다. AUTO-001은 **NG(미추적) 항목만 판단**하며 OK/Conditional OK/NOK 등급을 쓰지 않는다(사용자 결정 2026-11-23).
4. 코드를 고치면 `test/`의 가짜 서버 시험을 통과시킨 뒤 반영한다. 결과를 직관으로 예측하지 않고, 판정 규칙이 바뀌면 결과가 바뀌는 건수를 변경 전후로 실측해 보고한다.
5. **결과는 항상 새 파일**로 만든다. 기존 산출물·원본을 덮어쓰지 않는다.
6. Windows `.bat`·PowerShell·Python의 인코딩을 확인한다. 한글이 깨지지 않게 저장·시험하고, JSON은 가능하면 BOM 없는 UTF-8로 쓴다(기존 BOM 포함 JSON은 Python에서 `utf-8-sig`로 읽음). 인코딩 실패를 데이터 부재로 조용히 처리하지 않는다.
7. 실행 도구가 작업을 거부하면 다른 경로로 우회하지 않고 거부 사유를 확인해 보고한다.

## 6. 스킬 관리

1. 스킬 원본은 각 도구 폴더의 `SKILL.md`(예: `CA-automation/traceability/SKILL.md`, `qa-automation/tc-generation/.claude/skills/spec-to-tc/SKILL.md`)에 둔다.
2. 작업마다 실제 존재하는 스킬과 정본 기준을 확인한다. 아직 없는 기능(예: CA 판정 자동화)을 사용 가능한 기능으로 보고하지 않는다.
3. 스킬은 세부 절차를, 이 문서는 공통 원칙을 담는다. 스킬을 개정하면 이 문서·연관 자동화와 충돌하지 않는지 대조한다.

## 7. 지식 관리와 위키

1. 공식 표준·사내 승인 규정, 검증된 업무 지식, 실행 이력, 미확정 가설을 구분한다. 각 항목에 출처·적용 프로젝트·날짜·검증 상태를 기록한다.
2. 업무 배경과 결정 이력은 개인 위키(LLM Wiki, 예: `wiki/automation/`, `wiki/rules/`)에 두고, 저장소에는 실행에 필요한 규칙만 둔다. 둘이 다르면 차이를 보고한다.
3. 오류 사례는 재현 조건·영향·해결 방법·재검증 근거를 남긴다. 한 프로젝트의 예외를 공통 규칙으로 일반화하기 전 다른 프로젝트에 적용되는지 확인한다.

## 8. 산출물 검증과 보고

1. 생성·수정한 결과를 실제 파일에서 다시 연다. 원본과 출력물의 식별자, 대상 건수, 수식·값, 사용자 입력 영역, 다른 시트를 대조한다.
2. 데이터 미수집과 실제 0건, 판정 보류와 비적용, 시험 출력과 공식 승인본을 구별한다. 검증 실패·누락·제약은 숨기지 않고 보고한다.
3. 최종 보고에는 적용 범위와 기준, 변경 파일, 변경 전후, 검증 근거, 미확인 사항, 필요한 승인 항목을 포함한다. BP/GP 연결은 확인된 범위에 한해 제시한다.

## 9. 지침 변경 통제와 개정이력

1. 이 문서와 `SKILL.md`의 개정은 변경 사유·영향 범위·검증·승인 상태를 남긴다.
2. 아래 **미확정 사항**은 사용자가 확인하면 본문에 반영하고 목록에서 지운다.
3. 개정 이력은 아래 표에서 관리한다.
